Go Nilgris: Technical Website Documentation

A complete technical deep-dive into the Go Nilgris tour booking website. This document details the architecture, data flow, technology stack, and core functionalities.

1. Project Overview

1.1. Purpose

Go Nilgris is a full-stack web application designed for a tour operator in the Nilgiris region. It allows customers to browse tour packages, check availability, and book tours online. It also includes a comprehensive, locally-run admin panel for managing all aspects of the business, including tours, bookings, pricing, and site content.

3. Styling and UI

The application's look and feel is managed through a combination of Tailwind CSS for utility-first styling and ShadCN for pre-built, high-quality components.

The color scheme and theming are controlled by CSS variables defined in src/app/globals.css. This file sets up different themes (light, dark, forest, sunset, etc.) by defining HSL color values for primary, secondary, background, foreground, and other semantic color properties. 3.2. Fonts

The "Inter" font is used throughout the site. It is loaded from Google Fonts in the root layouts (src/app/(user)/layout.tsx and src/app/(admin)/layout.tsx) to ensure it is available on all pages.

3.3. UI Components

Components from ShadCN/UI are located in src/components/ui. These are not installed as a typical library but are part of the source code, making them fully customizable. App-specific components that compose these UI primitives are located in other subdirectories of src/components.

4. Data Flow and Firebase

Firebase Firestore is the single source of truth for the application's data. All interactions with the database are centralized in src/lib/firebase.ts. This file contains server-side functions for creating, reading, updating, and deleting data.

4.1. Firestore Data Model

Firestore is organized into several top-level collections:

CollectionPurposeDocument ID

4.2. Data Fetching Strategy

The application heavily utilizes Next.js Server Components to fetch data. This means that for most pages, data is fetched on the server before the page is sent to the client's browser. This improves performance and reduces the amount of client-side JavaScript.

Example: The tour details page (src/app/(user)/tours/[slug]/page.tsx) is a Server Component. It fetches the tour package details, its price, and its gallery images in parallel on the server and then passes this data as props to its child components.

// Simplified example from src/app/(user)/tours/[slug]/page.tsx

import { getTourPackageBySlug, getPackagePrice, getGalleryImages } from '@/lib/firebase';

async function getTourData(slug: string) {
    const tourData = await getTourPackageBySlug(slug);
    if (!tourData) {
        return { tourPackage: null, price: null, galleryImages: [] };
    }
    
    // Fetch price and gallery images in parallel
    const [price, galleryImages] = await Promise.all([
      getPackagePrice(slug),
      getGalleryImages(slug)
    ]);
    
    return { tourPackage: tourData, price, galleryImages };
}

export default async function TourPackagePage({ params }: { params: { slug: string } }) {
  const { slug } = params;
  const { tourPackage, price, galleryImages } = await getTourData(slug);

  if (!tourPackage) {
    notFound();
  }

  return (
    // ... JSX uses the fetched data
    <TourHeader name={tourPackage.name} ... />
    <TourTabs tourPackage={tourPackage} galleryImages={galleryImages} />
    <TourBookingCard tourPackageData={tourPackage} price={price} />
  );
}

4.3. Data Mutation Strategy (Server Actions)

Data creation, updates, and deletions are handled using Next.js Server Actions. These are functions defined on the server (marked with `'use server'`) that can be called directly from client-side components, typically during form submissions. This eliminates the need for manual API endpoint creation.

Example: The booking process uses a server action saveSuccessfulBooking to write the booking details to Firestore after a successful payment.

// From src/app/(user)/booking/actions.ts
'use server';

import { saveBooking as saveBookingToDb } from '@/lib/firebase';
import type { Booking } from '@/types';

export async function saveSuccessfulBooking(bookingData: Omit) {
    try {
        const dbId = await saveBookingToDb(bookingData);
        return { success: true, dbId };
    } catch (e) {
        console.error('Error saving booking to Firestore:', e);
        return { success: false, error: '...' };
    }
}

// Called from the client-side Razorpay payment handler
const options = {
    // ...
    handler: async (response: any) => {
        const bookingData = { /* ... construct booking data ... */ };
        const saveResult = await saveSuccessfulBooking(bookingData); // Server Action call
        if (saveResult.success) {
            router.push(`/booking/confirmation?id=${saveResult.dbId}...`);
        }
    }
};

4.4. Firebase Security Rules

The file firestore.rules defines the security model for the database, controlling who can read or write data to specific collections. Generally, public data (like tour packages) is world-readable, while write access is restricted. Bookings can be created by anyone but can only be managed by an authenticated admin.


// From firestore.rules
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
  
    // Tour packages should be publicly readable
    match /tour_packages/{packageSlug} {
      allow read: if true;
      allow write: if request.auth != null; // For now, only authenticated (admin) can write
    }

    // Bookings can be created by anyone, but only read/updated/deleted by an admin
    match /bookings/{bookingId} {
      allow create: if true;
      allow read, update, delete: if request.auth != null;
    }
    
    // ... other rules
  }
}

5. Key Functionalities

5.1. Tour Booking Flow

The booking process is a multi-step flow handled by the component at src/app/(user)/booking/page.tsx.

  1. Step 1: Details Selection: User selects a booking date and the number of passengers. The component fetches seat availability for the selected date in parallel.
  2. Step 2: Passenger Info & Seat Selection: The user fills out details for each passenger and selects seats from an interactive seat chart. The total price is calculated in real-time.
  3. Step 3: Payment: The user confirms the details and proceeds to payment. A server action (createPaymentOrder) is called to create an order with Razorpay. The Razorpay checkout modal is then displayed.
  4. Confirmation: Upon successful payment, Razorpay's `handler` function is invoked. This function calls another server action (saveSuccessfulBooking) to save the complete booking record to Firestore. The user is then redirected to a confirmation page with their unique booking ID.

5.2. Admin Panel

The admin panel is a powerful, locally-run dashboard for managing the site. It is located under the src/app/(admin) route group.

Critical Security Feature: The entire admin panel is disabled in production environments. The layout file src/app/(admin)/layout.tsx contains a check that prevents it from rendering if process.env.NODE_ENV === 'production'. This ensures the admin panel is never exposed on the live website. 

// from src/app/(admin)/layout.tsx
import { notFound } from 'next/navigation';

export default function AdminLayout({ children }: { children: React.ReactNode }) {
    // If we're in a production environment, don't render the admin panel.
    if (process.env.NODE_ENV === 'production') {
        notFound();
    }
    // ...
}

The admin panel includes management sections for:

  • Tours: Create, read, and update tour packages.
  • Bookings: View, search, edit, and delete all customer bookings.
  • Gallery: Add or remove images for tour galleries.
  • Pricing: Update the prices for each tour package.
  • Availability: Manually block or unblock seats for any tour on any date.
  • Notifications: View a passenger manifest for upcoming tours (today and tomorrow).
